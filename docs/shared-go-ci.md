# Общие Go CI и конфигурации линтеров

[FIN-372](https://finassist.youtrack.cloud/issue/FIN-372) переносит общие проверки Go-репозиториев в один источник: `fin-assist/go-service-template`. Реализация находится в `common/`, переиспользуемые workflows — в `.github/workflows/shared-*.yml`. Профили `service` и `library` сохраняют разные правила сервисов и библиотек. Подключение выполняется поэтапно; наличие общего исходника само по себе не означает, что все потребители переведены и приёмка завершена.

В этой части работы участвуют 15 Go-репозиториев из таблицы ниже. Android, contracts и infra не подключаются к Go-профилям. Их специализированные проверки не заменяются Go CI.

## Источник и неизменяемая ссылка

Решение владельца от 28.10.2026: потребитель закрепляет **полный commit SHA**, обновления приходят отдельными PR через Renovate, откат возвращает прежний SHA. Версионные теги для общего CI не создаются и не перемещаются.

У потребителя `.finassist-ci.json` задаёт один источник локальных настроек:

```json
{
  "revision": "<полный SHA из 40 строчных шестнадцатеричных символов>",
  "profile": "service",
  "gosec_g115": false,
  "squawk_smallint": false
}
```

Значение `revision` должно быть настоящим доступным коммитом `fin-assist/go-service-template`, содержащим общий код. Строка в примере — обозначение, bootstrap её отклонит. В `.github/workflows/ci.yml` все вызовы общего workflow закрепляются на том же SHA; параметр `revision` также совпадает с ним. Ссылка на ветку, сокращённый SHA или произвольный другой URL не заменяют этот pin.

Тонкий workflow потребителя оставляет у себя триггеры, минимальные permissions, явную передачу допустимого секрета и параметры профиля. Общие workflows выполняют Go/coverage, lint, совместимость публичного Go API библиотек, проверку SQL и сборку/проверку образа сервисов. У `assistant` отдельно включается образ fake-LLM, у `bank-bff` сохраняется HTTP smoke. Поведение образов задаётся разрешёнными параметрами, а не произвольной командой из вызывающего репозитория.

`common/versions.json` закрепляет версии линтеров, `common/configs/` хранит эталоны. `common/render_lint.py` получает префикс goimports из `go.mod` и создаёт `.finassist-ci/generated/.golangci.yml` и `.finassist-ci/generated/.squawk.toml`. У golangci явно задан `relative-path-mode: gomod`: исключения сохраняют смысл после переноса файла в подкаталог. Сгенерированные конфиги и скачанный кэш не редактируют и не коммитят.

## Карта профилей и осознанных различий

Для каждой строки источник общий: `fin-assist/go-service-template`, версия — **SHA из `revision` данного потребителя**, одинаковый для локальных команд и workflow. Таблица фиксирует параметры, а не объявляет все репозитории уже переведёнными. Столбцы G115 и smallint означают включение соответствующего исключения, `false` оставляет правило активным.

| Репозиторий | Профиль | `gosec_g115` | `squawk_smallint` | Особенности |
|---|---|---|---|---|
| `go-service-template` | `service` | false | false | Имя бинарного образца `service`; полный знаменатель coverage |
| `bank-bff` | `service` | true | false | Stateless, без PostgreSQL/SQL-миграций/Squawk; собственный HTTP smoke образа |
| `user` | `service` | false | false | Бинарный файл `user`; команды локальных dev-ключей остаются в сервисе |
| `bank-statement-data` | `service` | false | true | Единственное разрешённое исключение `prefer-bigint-over-smallint` (FIN-371) |
| `analytics` | `service` | true | false | Существующее исключение G115 |
| `assistant` | `service` | true | false | Существующее исключение G115; дополнительный образ и artifact fake-LLM |
| `go-library-template` | `library` | false | false | N/A только у исходного пустого шаблона и только после успешных suites |
| `go-identity` | `library` | true | false | Существующее исключение G115 |
| `go-idempotency` | `library` | true | false | Существующее исключение G115; отдельные release validation/publish scripts сохраняются |
| `go-outbox` | `library` | true | false | Существующее исключение G115 |
| `go-tombstone` | `library` | true | false | Существующее исключение G115 |
| `go-postgres` | `library` | false | false | Строгие coverage gates |
| `go-grpc` | `library` | false | false | Строгие coverage gates |
| `go-migrate` | `library` | false | false | Строгие coverage gates |
| `go-worker` | `library` | false | false | Без БД и SQL; строгие coverage gates |

Общий профиль библиотеки сохраняет FIN-322: запреты ядра процессного состояния, типизированный forbidigo, depguard и исключения тестов/`internal/pgtest`. Профиль сервиса позволяет сервису владеть процессом, сохраняя запреты обхода `finerr`, фреймворков, ORM и DI. G115 не отключается массово: параметр воспроизводит существующее решение конкретного репозитория.

Общий Squawk: PostgreSQL18, `assume_in_transaction=true`; исключены `require-lock-timeout`, `require-statement-timeout`, `prefer-bigint-over-int`. `prefer-bigint-over-smallint` остаётся включённым, кроме `bank-statement-data`. Renderer проверяет точное имя репозитория из `GITHUB_REPOSITORY` в Actions или точный GitHub origin локально; название чужого fork не даёт исключения.

## Локальные команды и кэш

После подключения репозитория:

```sh
make lint-config
make lint
make lint-migrations BASE_REF=origin/main
```

`lint-config` получает закреплённый источник и генерирует конфиги; `lint` запускает закреплённый golangci с этим же конфигом. `lint-migrations` сравнивает `BASE_REF...HEAD`, запрещает изменение/удаление/переименование существующих `migrations/*.sql` и запускает Squawk на добавленных `*.up.sql`. Сначала нужно получить актуальную ссылку базовой ветки. В PR CI использует фактическую базовую ветку, а не всегда `main`. Для `bank-bff` проверка миграций не подключается.

Маленький `scripts/common_ci.py` копируется из `common/bootstrap.py`. Без команды он печатает путь общего `common/`; команда `render` генерирует конфиги. Bootstrap скачивает только фиксированный HTTPS-репозиторий, получает точный SHA с таймаутом и проверяет origin, HEAD и чистоту кэша. Git replace refs отключены: локальные `refs/replace` не могут подставить другое дерево под закреплённый SHA. Проверка не вызывает `git status` и clean filters: raw commit/tree сверяются с их Git object IDs, а каждый файл checkout — с blob hash из этого дерева. Подмена `core.worktree`, скрывающие изменения stat/index-настройки и локальные filter-команды не определяют принимаемый код; лишние файлы и симлинки отклоняются. Формат и raw-чтение объектов описаны в [Git user manual](https://git-scm.com/docs/user-manual#_object_storage_format) и [git-cat-file](https://git-scm.com/docs/git-cat-file). Изменённый кэш отклоняется; исправление — удалить каталог именно повреждённой версии и скачать её заново. Статус успешного скачивания не подменяется локальными правками.

Кэш версий расположен в `.finassist-ci/<SHA>/`. Потребители запускают общий каталог отрицательных bootstrap-кейсов против своей локальной копии и проверяют её побайтовое совпадение с закреплённым исходником. Если меняется сам транспорт bootstrap, его копия обновляется явно вместе с pin: обычные изменения правил в `common/configs/` этого не требуют.

Обновление SHA создаёт отдельный каталог и сохраняет возможность вернуться к предыдущему коммиту. Уже скачанный чистый кэш позволяет bootstrap работать без сети. Полностью автономный запуск Go/npm-инструментов дополнительно требует их собственных заранее заполненных кэшей зависимостей.

При разработке самого общего исходника разрешён явный локальный путь:

```sh
python3 scripts/common_ci.py render --source ../go-service-template/common
```

Это выбор рабочего дерева для разработки и проверки изменений, а не настройка production-потребителя. В Actions локальный `--source` разрешён только для обычных `push`/`pull_request` self-tests с непривилегированными правами; привилегированные события, например `pull_request_target` и `workflow_run`, отклоняются. Вызовы общего CI потребителей используют закреплённый источник. Исполнять изменяемое локальное дерево с write-токеном/секретами нельзя.

## Проверки и границы доверия

Переезд сохраняет имена обязательных checks через небольшие итоговые jobs потребителя: `go`, `lint`, `image`, `api`, `migrations` по применимому профилю. Такой job зависит от результата общего workflow и не должен стать успешным при ошибке, отмене или неожиданном пропуске зависимой проверки. Вложенные имена reusable jobs не заменяют старое required имя. На пилотах проверяются реальные опубликованные check contexts и их связь с итоговым SHA.

Снимок branch protection `main` от 28.10.2026, полученный чтением API без изменений настроек:

| Репозитории | Required contexts |
|---|---|
| `go-service-template`, `user`, `bank-statement-data`, `analytics`, `assistant` | `go`, `lint`, `image`, `migrations`, `Renovate policy tests`, `Renovate runtime contract` |
| Все девять библиотек, включая `go-library-template` | `go`, `lint`, `api`, `migrations`, `Renovate policy tests`, `Renovate runtime contract` |
| `bank-bff` | API branch protection вернул `Branch not protected` |

Для защищённых строк API вернул `strict: true`, checks от GitHub Actions (`app_id: 15368`). `bank-bff` нельзя считать защищённым по аналогии с остальными. В той же сверке API rulesets с учётом inherited rulesets вернул пустой список для всех 15 репозиториев; отдельная защита rulesets в этом снимке отсутствует. Настройка или изменение защит остаётся действием владельца и не выполняется этим переходом. Перед merge проверяется, что существующие требуемые контексты продолжают появляться; если потребуется настройка владельца, её явно выносят в план перехода.

Go unit/integration/API независимо сохраняют total80 всего production-знаменателя, PG18, race/count1, таймауты, inventory тестов, валидацию непустых выполненных suites и coverage artifacts. Combined не компенсирует провал уровня. У сервисов не появляется библиотечное исключение `internal/pgtest`; у библиотек исключается только точный пакет `<module>/internal/pgtest`, сами его тесты выполняются. N/A остаётся ограниченным фиксированной identity исходного `go-library-template`. Ни новый репозиторий с прежним module path, ни параметр профиля не наследуют это разрешение.

Компилятор тестов берётся из `go.mod`: `setup-go` сохраняет `GOTOOLCHAIN=local` для inventory и collectors. Закреплённые анализаторы coverage/gorelease и script fixtures запускаются отдельно с `GOTOOLCHAIN=auto`, поскольку их минимальная версия Go может быть выше версии проекта. Это не меняет компилятор production-кода и не снижает пороги.

Coverage guards и относящиеся к ним проверочные скрипты на данном этапе остаются в потребителях: это самостоятельные защиты, а не конфигурация линтера. Аналогично сохраняются FIN-264 и проверка совместимости публичного Go API, immutable SQL, up/down/up и специальные smoke/artifacts сервисов. Дубли удаляются только после фактической замены общим источником.

Обычный PR/fork CI имеет `contents: read`, checkout без сохранения credentials и не получает write-доступа. Передача `GO_MODULES_TOKEN` явная, без `secrets: inherit`; общий Go/API CI использует его только на доверенном `push`, а не при выполнении PR-кода. У образов остаётся передача токена через BuildKit netrc secret вместо build args или логов. Отсутствие доступа к приватному модулю не является основанием выдать секрет недоверенному PR или признать невыполненный gate успешным.

Привилегированные Claude/release/Renovate-controller workflows остаются локальными намеренно. Их триггеры, проверки происхождения PR, отдельные права, Environment, секреты и версии контроллера различаются. Например, у `bank-bff` уже есть проверка источника PR до write-enabled Claude; унификация не должна её стереть. Контроллер Renovate продолжает исполнять проверенный код `main` и не читает исполняемый PR-код/artifacts с write-токеном. Владелец по-прежнему выпускает теги библиотек сам.

## Обновление правила и откат

Общее правило меняется в `common/` одного source PR. Его self-check workflow проверяет рабочее дерево: bootstrap/render, workflows и реальные разрешённые/запрещённые lint-случаи. После ревью и команды владельца source коммит становится доступным потребителям.

Сверка 28.10.2026: `RENOVATE_POLICY_ENABLED=true` у 11 существующих Go-репозиториев; их рассмотренный `renovate-base.json` публикуется существующим контроллером в `base.json` ветки `renovate-policy` после merge. У `go-grpc`, `go-migrate`, `go-worker` флаг равен `false`, поэтому новые managers/group размещены непосредственно в действующем `renovate.json`, без зависимости от baseline-sync; прежние presets, метаданные FIN-211 и запрет native automerge сохранены. У `bank-bff` новый прямой `renovate.json` также не активирует контроллер. Наличие флага/ветки не подменяет проверку конкретного запуска после merge; активация выключенных контроллеров не входит в FIN-372.

Renovate обновляет ссылки на общий source согласованной группой: SHA workflows, входные `revision` и `.finassist-ci.json` должны перейти вместе. Обновление имеет собственный PR и CI каждого потребителя; изменяемая ветка общего репозитория не подключается напрямую. Правила FIN-211 для подтверждённых Renovate обновлений сохраняются; настройка группы не разрешает вручную сливать обычные PR.

Граница доверия — однократное ревью изменения общих правил в source PR и явный merge владельцем в source `main`, затем проверяемые обновления зависимостей потребителей. Один владелец управляет источником и перечисленными репозиториями FinAssist. Обычные изменения исходника не получают права на автоматический merge: сохраняется проектный процесс ревью и отдельной команды владельца. При уже включённой и проверенной автоматизации FIN-211 подтверждённые Renovate PR с обновлением source SHA остаются допустимыми dependency updates; требование отдельного Dashboard approval для этой группы не добавляется. Такой переход доверяет рассмотренному source, а не независимая проверка неизменности политики каждым потребителем: CI нового SHA сам по себе не доказывает, что правила не были ослаблены. На изменение total80, запретов линтеров, race или security gates смотрят в source review. Настройка группы не подтверждает активацию контроллера в конкретном репозитории.

Полный SHA и фиксированный URL гарантируют выбранные байты, но не авторство или принадлежность коммита `main`: GitHub может отдавать через URL upstream и объекты fork network. Bootstrap не проверяет предковость `main`; его проверки origin и Git-объектов нельзя считать такой проверкой. Произвольный ручной bump SHA требует сверки с рассмотренным source PR владельцем. Автоматический lookup Renovate настроен на `main`, а не на произвольные SHA из PR.

Для первого перехода закреплён source `699febc65bbf66431845b1f7ad59db0d6855368f`, содержащий общую реализацию PR #51. До merge потребителей владелец должен слить source PR **merge-коммитом**, сохранив этот SHA в истории `main`. Squash/rebase меняет эту предпосылку: тогда сначала нужен отдельный согласованный bump всех pins на итоговый рассмотренный SHA `main` и повторный CI. Обновления только source-тестов и документации после закрепления не требуют менять pin исполняемой реализации. Сам FIN-372 не разрешает агенту выполнять merge.

Откат — revert коммита обновления pin в потребителе: возвращаются прежние SHA во всех местах одной согласованной правкой. Старое содержимое кэша не переписывается, теги не передвигаются. Правку общего правила или его откат не нужно вручную повторять в копиях конфигураций: потребители выбирают старый либо новый неизменяемый источник.

## Порядок перехода и приёмка

1. Подготовить общий source, self-checks, карту профилей и сверку защит. Source SHA должен существовать на GitHub до запуска consumer workflow, который на него ссылается.
2. Подключить два пилота: один обычный stateful сервис и одну библиотеку. Проверить полный CI, локальное совпадение конфигов, положительные/отрицательные lint-случаи, реальные имена required checks, обновление SHA и откат.
3. После пилотов подключить оба шаблона. В инструкциях создания нового репозитория менять только его module/import path и описание. **Не выполнять глобальную замену** `fin-assist/go-service-template`: координаты общего source должны остаться исходными. Фиксированную identity N/A в библиотечном guard также не переписывать.
4. Подключить остальные Go-репозитории, сохраняя параметры таблицы, HTTP smoke `bank-bff`, fake-LLM `assistant` и особенности release workflows. Удалять только заменённые дубли; README/AGENTS и локальные команды обновлять в том же PR.
5. Для каждого итогового SHA сопоставить прежние gates и новые результаты: CI, coverage suites, SQL/compatibility, artifacts, fork/secrets и lint probes. Проверить отсутствие открытых замечаний и оставшихся пунктов задачи.

Полная приёмка требует реальных успешных контрольных прогонов пилотов и всех подключённых репозиториев. Локальные self-tests общего кода, статическая карта или подготовленный consumer diff не подтверждают завершение всего перехода. Merge любого обычного PR, изменение branch protection, deployment, выпуск тегов и UI-прогоны требуют соответствующего отдельного разрешения владельца; FIN-372 их автоматически не разрешает.
